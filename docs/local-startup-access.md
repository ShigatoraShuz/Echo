# Local startup and account access

Use one startup method. For the complete application, run `.\scripts\start-local-core.ps1` from Echo. This starts the Python model service, frontend on 3000 and Express on 4200; do not run a second `npm run dev`. Stop previously launched development instances with Ctrl+C in their own terminals before restarting. The launcher checks all three ports and never terminates an existing instance automatically.

For application-only development, use `npm run dev`. Separate workspace commands (`npm run dev -w frontend`, `npm run dev -w backend`) remain supported when intentionally running each service once. These commands share a launcher that preserves existing proxy exclusions and adds localhost/127.0.0.1/IPv6 loopback to the child process environment. Global proxy settings and protected environment files are unchanged. Root startup checks both application ports before spawning either process; workspace commands check their own port. Occupied ports fail explicitly instead of choosing another frontend port.

The original error was reproduced as a local transport failure: Node could not reach the listening backend with its inherited proxy settings, while a process-local loopback exclusion returned the expected anonymous 401. Existing terminals do not acquire environment changes made in another terminal. This evidence establishes a transport issue, not whether any particular account currently has valid access.

The account gateway now treats HTTP 401/missing session as requiring login. Connection failures, timeouts, backend failures and malformed/unknown access decisions fail closed with `access_service_unavailable` and a temporary-unavailability message. The old `access_check_unavailable` URL remains readable with the updated wording. Both login pages offer Retry account access, retain the safe original destination and do not automatically bounce a cached session back through a failing gate. No cookies, sessions, eligibility checks, account restrictions or privacy preferences are cleared or bypassed.

Diagnostics log a generated UUID request ID, bounded failure category and HTTP status only; the UUID is forwarded to Express. Tokens, cookies, user IDs, backend response bodies and raw exception messages are omitted. Rejected sessions still require authentication; access-service failures do not prove session expiry.

Verification: shared-launcher tests cover unchanged parent environment/proxy settings, occupied-port rejection and child Node fetch with environment proxies enabled. Authentication UI/gateway tests cover invalid sessions, backend failures, timeout, malformed payloads, all access decisions and professional retry-loop prevention. Frontend/backend TypeScript checks and targeted backend authentication/access tests are run. Interactive login with a real account remains unverified: no user credentials, sign-in submissions or database writes are performed by this change.
