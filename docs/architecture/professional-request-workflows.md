# Professional request workflow additions

Local implementation, 14 October 2026; not deployed. Supplements the verified professional module contract. Existing owner creation/list/detail/revoke and professional claim/case APIs remain compatible. Authentication, application eligibility, rate limiting and no-store responses are unchanged.

## BE-009 owner changes

Paths are relative to `/api/v1`. Both return the existing `{ success: true, data: { request: RequestSummary }, meta }` envelope, without plaintext message, preferred time or owner identity.

- `PATCH /professional/my-requests/:requestId`: strict `{ summary: trimmed 20..4000 characters, preferredTime: trimmed 0..240 characters }`. Both fields required. Uses the verified owner; encrypts both fields through the existing encryption service. Only submitted, unassigned requests with current sharing, active organization and eligible owner can be updated. Organization, journals, consent version/expiry, assignment and actor cannot be changed or overposted.
- `POST /professional/my-requests/:requestId/cancel`: empty body. Withdraws only the owner's submitted, unassigned request. Existing `closed` status represents withdrawal; assignment remains null and sharing is revoked. `request.withdrawn` identifies the distinct action in audit history. Retrying the same withdrawal returns the same state without another audit. Withdrawal is permitted after organization suspension; application authentication/eligibility guards still apply.
- Assigned/scheduled cases require professional case handling; owner withdrawal does not close those cases or cancel appointments. No new `canceled` request status, deletion, automatic transfer, or consent renewal is introduced.
- Both SQL RPCs lock the request row, the same serialization point used by claims. If claim wins, owner changes conflict; if withdrawal wins, claim conflicts. Audit failure rolls back the change. No evidence, note or journal text enters audit records.
- Missing/unowned request: 404. No longer editable/currently shared: 409 `REQUEST_NOT_EDITABLE`. Invalid input: 400. Unknown database failures: fixed 503, without diagnostics or ciphertext. Owner actions retain existing non-MFA owner semantics; they grant no professional authority.

## BE-010/011 claims and lifecycle

Next local migration: `20261014110000_professional_claim_lifecycle.sql`, after the three migrations above. It replaces claim/terminal-transition/assigned-author functions and adds a transition trigger plus a private current-clinician predicate. It does not rewrite existing rows. Invalid legacy transitions fail closed; deployment must inspect legacy lifecycle consistency first. Both owner-action and lifecycle migrations were executed locally in PGlite only.

- Claims lock the request row and recheck active organization, clinical membership, profile eligibility and a matching approved unexpired credential. Repeating a claim by the same eligible assignee returns the current assigned/scheduled request without duplicate audit. A competing actor or terminal request conflicts. Claims remain MFA protected at HTTP.
- Closure similarly permits a same-assignee, still-authorized retry without duplicate audit. Active appointments prevent closure/decline. Lost membership/assignment produces 403; absent request 404; no-longer-claimable/invalid lifecycle 409; unknown database failures fixed 503. Error responses do not disclose SQL text.
- The transition trigger permits existing assignment/scheduling/cancellation/terminal flows and owner withdrawal, while rejecting implicit changes of tenant, owner, assignee, reopening, and scheduling without a confirmed appointment. Existing states remain `submitted`, `assigned`, `scheduled`, `closed`, `declined`.
- Note/referral author triggers take the same request row lock before checking live clinical eligibility, assignment and writable state. A closure that commits first prevents the write; a write that acquires the lock first completes before closure. Existing ciphertext and audit history are preserved.
- Follow-ups will be separate records under BE-022, not invented case states. Transfers require an explicit authorized transaction under BE-018 and remain unavailable; the trigger deliberately prevents implicit reassignment. No decline HTTP endpoint, closure reason, transfer or reopening API is introduced here.
- Forward fixes are preferred. Rolling back the application must not restore insecure eligibility checks or drop the transition guard without a compatible owner-reviewed plan. No data-destructive rollback is supplied.

Tests: `professional-lifecycle.database.test.ts` covers serialized competing outcomes, safe retries, rollback, credential/account checks, supported lifecycle and forbidden transitions; `professional-authorization.test.ts` covers typed conflict/denial mapping. Independent-connection PostgreSQL concurrency remains unexecuted because no PostgreSQL server/CLI or Docker is available on PATH. Do not represent PGlite's serialized submissions as a live multi-connection race test.

## BE-012 server queue filters

Existing MFA-protected `GET /professional/organizations/:organizationId/queue` now accepts strict optional query fields: `status` (the five existing states), `assignedTo` (UUID, `me`, or `unassigned`), `createdFrom`/`createdThrough` (inclusive UTC dates), `sort` (`newest` default, `oldest`, `updated`), `limit` (1–100, default 100), `offset` (0–10000, default 0). Dates must be valid and ordered. Unknown, repeated/object-valued, invalid or excessive parameters are rejected before database reads. Date-through is implemented as an exclusive next-day UTC bound.

Filters always combine with the authorized organization; assignee selection does not grant case access. Responses retain `requests` metadata and add `page: { offset, limit, total, hasMore }`. `total` is the exact number matching the server filters, not the page length or all-state dashboard count. Stable ID ordering breaks date ties. Missing count metadata fails closed. Offset pagination is bounded but not a stable snapshot across concurrent updates; refresh when the queue changes. No original journal, owner identity, message or credential evidence is projected.

This change needs backend deployment but no additional migration. Existing frontend calls and capped-list presentation remain compatible; the API adapter additionally accepts filters/page metadata. Server-wide dashboard metrics are a separate BE-013 contract. Tests: `professional-queue.test.ts` (14 filter-aware service/HTTP regressions) and frontend API adapter coverage.

## BE-013 dashboard

MFA-protected `GET /professional/organizations/:organizationId/dashboard` returns exact organization pending counts, own active/scheduled counts, the latest 3 scheduled cases, and earliest 5 upcoming own proposed/confirmed appointments with exact appointment total. No client message, notes or location hints. `dashboard_overview` locks eligibility rows, builds counts/lists in one statement snapshot and commits `dashboard.viewed` before delivery. The frontend labels legacy/service-unavailable loaded-page fallback and conceals data on access failures. Local migration: `20261014120000_professional_dashboard.sql`; deploy before enabling the endpoint. Missing RPC never produces invented totals.

## BE-014/015 transactional detail and consent

Local migrations `20261015100000_professional_case_snapshot.sql` and `20261015110000_professional_consent.sql` follow lifecycle/credential dependencies. Professional detail uses `case_snapshot`: current assignment, active organization/profile/membership and approved linked clinical credential are checked while rows are share-locked. Sensitive children use explicit projections, selected journal IDs and database-clock expiry/revocation. `case.opened` must commit with the read. Service rechecks current assignment/membership/sharing before decrypting. No authorization-by-fallback if the new RPC is absent; deploy migration before backend. Owner detail contract remains unchanged.

An optional `timeline: { events: [{ id, action, at }], hasMore, limit: 200 }` adds the latest allowlisted case actions, returned oldest first. It excludes actor/subject identities, content, access events and internal diagnostics. No new endpoint or unrestricted audit API. Older frontend responses continue to show clearly labeled record timestamps.

Existing `professional-request-v1` permits the request message, preferred time and up to 3 owner-selected journal title/body snapshots, for the assigned eligible practitioner in that request's organization. The purpose remains professional support for that case; no blanket journal/analysis access. Version, selected IDs, grant timestamp and original 30-day expiry cannot be edited or renewed; revocation is irreversible and retry-safe with one audit. Closure still does not implicitly revoke sharing. Expired/revoked professional reads exclude shared ciphertext at SQL and plaintext at service projection. Notes/appointments retain separate professional authorization. Transactions cannot recall already delivered responses; independent-connection races still require PostgreSQL integration testing.

No assessment-sharing API is enabled. Actual self-completed PHQ-8 records exist in `insights_service.phq8_assessments`; journal-analysis estimates are a separate source. Both remain outside the existing consent version. A versioned explicit owner-selected assessment grant and professional projection are BE-016 follow-up work. No User Side consent UI or records were changed. These additive local migrations change no historical grants and must not be rolled back by restoring revoked sharing or dropping audit history.

## BE-017 notes

Local migration `20261015120000_professional_notes.sql` follows case snapshot/consent. Existing notes become final with original creation timestamps, body ciphertext unchanged. Existing `POST /professional/cases/:requestId/notes` accepts `{ body: trimmed 2..4000, submissionId?: UUID, state?: "draft" | "final" }`; default final preserves existing saves. Optional submission ID deduplicates per case/author; without it the server generates a new UUID, so legacy retries are not guaranteed duplicate-free. Response adds state/revision beside noteId. Reuse with different body/state returns 409 without exposing previous content; comparison decrypts only the same author's authenticated stored record, without a plaintext hash.

MFA-protected `PATCH /professional/cases/:requestId/notes/:noteId` accepts strict `{ body: trimmed 2..4000, expectedRevision: integer >=1, finalize: boolean }`. Only the active assigned author can edit a draft in an open case; revision conflict returns 409. Final notes are immutable. A same-content finalization retry acknowledges the existing finalized revision without duplicate audit. SQL locks case then note, rechecks reviewed clinical eligibility, and commits audits atomically. Browser roles have no direct execution/table access. Own drafts and case final notes are returned; another author's drafts are excluded, including after later transfer. No owner-note sharing.

The detail response advertises `notesLifecycleAvailable` only when the SQL lifecycle function exists. The existing frontend editor uses submission IDs when supported and labels returned drafts; it still saves final notes and does not offer draft editing controls. Uncertain outcomes still require a refresh/review, never automatic resend. Deployment precedes backend activation; rollback must preserve draft/final metadata and final immutability, not drop columns/history or let an old app show drafts as final.

## BE-018 handover and closure

Local migration `20261015130000_professional_case_handover.sql` follows notes. MFA-protected `POST /professional/cases/:requestId/transfer` accepts strict `{ targetUserId: UUID, reason: trimmed 10..2000, submissionId: UUID }`. Current assignee and target must both have current reviewed clinical eligibility in the same active organization. Case must be assigned with no proposed/confirmed appointment or unfinalized author draft. Request, eligibility rows, encrypted transfer receipt and `request.transferred` audit commit together. Transition trigger accepts only a matching transfer receipt from the same database transaction; client flags cannot enable reassignment. Old assignee immediately loses subsequent detail access. Retry uses the same submission ID and reason; a changed target, assignment or reason conflicts. No new request status or cross-organization transfer. No recipient-picker UI is implemented; the frontend API adapter is available.

Existing `POST .../close` accepts optional `{ reason: trimmed 2..2000 }`, preserving empty-body callers. Closure reason is an encrypted professional record in a separate RLS-protected table with no browser/service-role table grants; no reason appears in audit or ordinary response. Closure retains eligibility/assignment and active-appointment checks, commits reason with the status audit, and never overwrites a historical reason on retry. Existing frontend dialog is capability gated (`closureReasonAvailable`), keeps optional text in memory only and clears on dismissal. Reopening remains unsupported; closure does not revoke consent. Returned metadata remains `{ request }`; transfer adds `transferId`. New tables are not an external referral or notification system. Rollback must retain transfer/closure receipts and assignment history; never restore old assignments automatically.

## BE-019 audit outcomes

Owner case detail records `request.owner_viewed` before projection, without querying notes. Administrator audit-list reads record `admin.audit_viewed` and add `requestId` to their safe event projection. Both fail closed if recording fails. Existing professional case/dashboard SQL reads and mutations retain atomic successful-action audits; no plaintext reason, note, journal or credential evidence enters events. Read audits record database access, not proof that a network response reached its recipient.

The existing security middleware now categorizes professional routes for allowed/denied/failed HTTP outcomes, including 404/conflict/service failure. Payload contains only event type, correlation ID, hashed actor, outcome and status. Existing 401/403/rate/admin categories retain precedence. This global security sink is asynchronous/best-effort and logs only delivery failure correlation; it is not a durable business-event outbox (BE-025). No new external logging destination or private case-existence detail is introduced.

## BE-020/021 appointments

Local migrations `20261016100000_professional_appointment_lifecycle.sql` then `20261016110000_professional_scheduling_constraints.sql` retain owner acceptance and practitioner MFA cancellation. All writers lock request before appointment; proposals/rescheduling serialize by practitioner too. Proposal validates finite future times, positive duration up to two hours, supported mode and encrypted meeting detail. Expired proposals cannot be accepted; owners may still cancel. Current linked credential eligibility is required, not only a copied expiry date. Confirmation/rejection/cancellation retry without duplicate audits. Wrong owner/assignee returns a privacy-safe denial; invalid time is 400, unavailable/expired/conflicting appointment 409, unknown SQL failure 503 without diagnostics.

New MFA-protected `POST /professional/appointments/:appointmentId/reschedule` uses existing proposal fields. Only the current assigned professional may replace a proposed/confirmed appointment. Cancellation, new proposal, replacement link and audits are one transaction; failure preserves the original. New offer requires fresh owner acceptance. Repeating the same replacement returns its record; changed timing/mode or meeting detail conflicts. The API adapter is available; existing UI keeps explicit cancel/propose controls.

The GiST constraint (`btree_gist` extension) prevents overlapping proposed/confirmed ranges for a practitioner across organizations, including direct SQL and simultaneous inserts; adjacent intervals and canceled history are allowed. Existing one-active-appointment-per-request index remains. Deployment requires extension availability and an overlap/finite-time preflight, with owner-approved resolution of any legacy conflicts. Do not silently cancel old records or drop the constraint to pass migration. No working-hours calendar/provider availability integration is implied. PGlite exercises PostgreSQL constraint behavior on one connection; independent-connection race tests are still pending.

## BE-022 follow-ups

Local `20261016120000_professional_follow_ups.sql` follows handover. MFA-only `GET/POST /professional/cases/:requestId/follow-ups`, `PATCH .../:followUpId`, and `POST .../:followUpId/complete` use current assigned clinical eligibility, case/organization isolation and atomic audit. Create accepts title (trimmed 2..240), ISO dueAt and submission UUID; editing accepts title/dueAt/expectedRevision; completion accepts expectedRevision only. Actor, organization and responsible practitioner are derived in SQL. List returns items/total/hasMore/limit (100), pending first then due date. Titles use existing encryption and explicit response projection; no plaintext in audit or ordinary logs.

Create retries deduplicate the original intent. Edits conflict on stale revision; completing the same revision retries safely. Pending work transfers with an authorized case handover. Closed cases permit completing existing follow-ups, but no new work or edits. No new request state or external reminder delivery is implied. New tables have no browser or direct service-role grants; only authorized RPCs. API adapter is ready; existing frontend preview remains synthetic and dashboard follow-up aggregation is not yet enabled. Deployment must precede real UI activation; rollback must preserve encrypted records and completion history.

## BE-023 referrals

Local `20261016130000_professional_referral_lifecycle.sql` follows follow-ups and reuses the existing referrals table. Existing POST accepts optional submission UUID (legacy callers get a server UUID); trusted `record_referral` checks current assignee and case state, validates resource name/HTTPS reference, deduplicates intent and records history atomically. It does not contact the URL or approve a destination organization. There is no verified referral destination registry in this contract.

MFA-only GET `/professional/cases/:requestId/referrals` returns the latest 100 items with exact total and status/history. PATCH `.../:referralId` accepts only `{ status: "completed" | "canceled", expectedRevision }`. Recorded referrals can resolve once, including after case closure; neither terminal state can reopen or imply external acceptance. Retry of the same transition is safe. History contains status/time/revision, not actor identities or case content. Existing records retain original timestamps with no fabricated historical transition events. Responses explicitly report `delivery: "not_integrated"`; no external transport exists. Direct service-role inserts are revoked, so deploy this migration and the compatible backend together; rollback must retain history and RPC protections. Current frontend creation remains compatible; lifecycle controls require later UI integration.

## BE-024/025 notifications and durable events

Local `20261016140000_professional_notifications.sql` then `20261016150000_professional_events.sql` reuse existing notification storage and the in-app preference. Ordinary inbox rows contain generic text without case/org/content references. Private links provide MFA-only GET `/professional/organizations/:organizationId/notifications?status=all|unread` (50 latest, exact total), and PATCH `.../:notificationId/read` (empty body, stable read timestamp). Current clinical membership, tenant and assignment are authoritative; personal/unrelated notifications are excluded. No shared notification service or User Side source is changed.

Allowlisted workflow audits enqueue metadata atomically. Trusted batch processing locks pending rows, rechecks intended recipient/current assignment/eligibility/preferences, and delivers to the existing notification table with event-key uniqueness. Each delivery failure rolls back its own insertion and records only `DELIVERY_FAILED`; retries back off up to an hour, then enter explicit failed status at eight attempts. Service-only retry RPC permits operator recovery after fixing the cause. No plaintext or SQL diagnostic enters the queue. Changed assignments, opt-out and stale/completed follow-up reminders are suppressed rather than sent to another recipient. Due reminders deduplicate by follow-up ID/revision; no guaranteed notification time or external delivery is promised.

`ProfessionalEventService.runBatch()` and local-only `backend/scripts/professional-events.mts` are executable foundations. No automatic production timer is enabled: deployment must schedule bounded batches, monitor failures/backlog and approve operator recovery. The local command refuses nonlocal Supabase hosts; it was not run against any database in this mission. PGlite covers transactional rollback/retry; multi-connection worker contention remains unverified. Rollback must preserve pending/failed events and delivery keys; never delete the outbox to hide failures.
