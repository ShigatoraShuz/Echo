# ECHO professional portal: feature design and release backlog

## Product decision

Build an adult-only, multi-organization support workflow for approved counselors, psychologists, social workers, coordinators, organization administrators, ECHO administrators, and ECHO users. ECHO is a wellbeing and referral product, not an emergency monitoring service or a diagnostic system. The professional workspace should help a human professional receive a user-initiated request, arrange support, keep a restricted record, and close the loop with the user.

The first local implementation is present in the repository; it is **not a launched service**. Its Supabase migration and hosted API schema setup have not been applied or verified against a live project. This document distinguishes that local baseline from the work required for a pilot.

### Design choices

| Approach                                                         | Benefit                                                                         | Cost or risk                                                       | Decision                                  |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------ | ----------------------------------------- |
| One shared ECHO tenant for every partner                         | Fastest UI                                                                      | Cross-organization exposure is too easy                            | Reject                                    |
| A separate deployment for each partner                           | Strong separation                                                               | High operational cost, fragmented user flow                        | Defer unless partner contracts require it |
| One portal with server-enforced organization and case boundaries | Fits the current Express/Supabase design and multiple organizations from launch | Requires negative authorization tests for every query and mutation | **Use**                                   |

Continue the existing path: Next.js UI -> authenticated Express API -> `professional_service` schema. The browser must not query professional tables directly. ECHO account verification and professional approval remain separate. One user may have memberships in several organizations; every action is scoped to one organization and, for private case data, the assigned professional. Multi-organization membership must never merge queues or case records.

## User and professional authentication journeys

Use **one Supabase identity and the existing ECHO sign-in methods** for both audiences. Give each audience a clear entry page and destination; do not create a second password store or treat a selected portal as proof of a role. A professional may also use ECHO as an ordinary user, so the workspace switch changes context without changing identity or sharing private journal data.

| Stage                  | ECHO user                                                                                              | Professional                                                                                                                                                             |
| ---------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Entry                  | `/signup` or `/login`; existing email code, password, or Google sign-in                                | Dedicated `/professional/login` page reuses the same sign-in controls; public sign-up creates only an ordinary ECHO account                                              |
| Account gate           | Verified email, active account, adult eligibility, current policies, completed onboarding              | The same account gate completes first; ordinary account verification alone never grants professional access                                                              |
| Role gate              | No professional membership needed for `/professional/request` or `/professional/my-requests`           | `/professional/access` checks each organization membership, role, organization status, credential expiry, and MFA readiness through the backend                          |
| Successful destination | Safe original user URL or `/dashboard`; a user-initiated support request returns to its safe deep link | Safe original professional workspace URL or `/professional`; show an organization selector when more than one membership is active                                       |
| Not ready              | Show the existing email/age/policy/onboarding step; sign-in failures stay in the sign-in form          | Show distinct pending approval, no membership, suspended, expired credential, MFA setup/challenge, and access-service error states, with next action and no case content |
| Session exit           | Existing global sign-out                                                                               | Visible professional sign-out uses the same global session; “My ECHO” switches workspaces without signing out                                                            |

The first pilot keeps ECHO-admin provisioned staff approval. Staff create or use a regular ECHO account, then ECHO reviews and attaches the organization membership. A public “professional sign-up” button must never self-assign a clinical role. Partner-managed invitations belong to F12 after the pilot; they may simplify account linking but still require ECHO's final credential review.

The protected `/professional` prefix contains both audience types. `/professional/request` and `/professional/my-requests/*` remain ordinary authenticated-user routes. Only the workspace routes (`/professional`, `/professional/cases/*`, and later queue/calendar/settings routes) require professional membership and MFA. Enforce that distinction in Express for every sensitive endpoint, with a matching route-level UI gate; do not put a blanket professional-role check on the entire prefix.

Preserve only safe same-origin deep links through sign-in and MFA. A professional login should reach `/professional/access` before opening a requested workspace page. The access page must clear any case data on denial or session change and must not reveal whether an arbitrary email belongs to a professional account.

## Authorization and data rules

1. All professional reads and writes go through authenticated Express endpoints. `professional_service` remains service-role-only at PostgREST and inaccessible to `anon`/`authenticated` clients.
2. Every request is scoped by active organization, active membership, role, assignment, MFA, credential validity, and user sharing state where private shared content is involved. Hiding a UI action is never the authorization check.
3. Coordinators and organization admins may view queue metadata and operational aggregates, not private request text, journal snapshots, or practitioner notes unless they separately hold an active clinical role and are assigned the case. Keep the current single membership role model until a reviewed requirement justifies multiple roles in one org.
4. Sharing a journal snapshot is explicit, limited to up to three entries, and never includes Buddy, facial data, or AI analysis. Reassignment within the chosen organization follows the user's organization-level consent; transfers to another organization require new consent.
5. Encrypt free text and meeting details with the existing ECHO encryption service. Do not put private text in URLs, analytics, notifications, logs, or audit event payloads. Audit actor, action, organization, request ID, and time.
6. The adult eligibility rule remains. Serving minors, guardians, or school-issued accounts requires a separate safeguarding and consent design before any code changes.
7. AI summaries and automated risk labels are outside the pilot. If pursued later, model unavailability must show “unavailable,” and a human owns all decisions.
8. Authentication establishes identity, not professional entitlement. The backend derives entitlement for each organization on each request; never trust a URL, local storage flag, or client-supplied role.
9. MFA is required before professional queue/case access. Admin membership or credential changes also require recent authentication. User support-request routes remain available without professional MFA.

## Success measures for a pilot

- 100% of sampled cross-organization and unassigned-case access attempts return no private content.
- 100% of credential expiry, staff suspension, organization suspension, consent revocation, and sharing expiry scenarios remove protected access immediately.
- Every submitted request has a visible status; every state change is audited; no response-time promise exceeds the partner's actual service hours.
- At 320px and 200% zoom, core actions remain reachable; keyboard and screen reader users hear loading, success, and error states.
- Measure median first response and unassigned-request age per organization without exporting private content. These are operational measures, not clinical efficacy claims.
- All three existing sign-in methods preserve a safe user or professional destination; inactive, pending, expired, suspended, AAL1, and cross-organization sessions never reveal professional case data.

Security acceptance follows OWASP's server-side authorization and sensitive logging guidance: https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html and https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html .
