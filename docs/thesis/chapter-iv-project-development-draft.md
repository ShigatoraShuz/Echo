# Chapter IV: Project Development — repository-grounded draft

**Draft status (6 October 2026).** The following paragraphs are written for insertion into the unfinished sections of Chapter IV of `CH-4.pdf`. They describe the implementation visible in the repository and use future tense for AI components that still require integration and validation. This is a development account, not a report of completed model testing, clinical validation, or production deployment. Section numbers follow the uploaded paper. The accompanying [service schema reference](./service-schema-reference.md) lists the tables separately by PostgreSQL schema.

## 4.1.2 Database Architecture / Schema — suggested correction

Echo uses one Supabase PostgreSQL database organized into logical schemas for the major application domains. The schemas named `user_service`, `journal_service`, `buddy_service`, `grounding_service`, `insights_service`, `notification_service`, `verification_service`, and `ai_analysis` group related tables and access rules within the same database. The `auth_provisioning` schema supports registration and policy acknowledgement, while Supabase Authentication manages account identities. These names describe data ownership boundaries; they do not represent separate physical databases or independently deployed microservices. The `public` schema also contains a restricted analysis status projection and older compatibility tables. Accordingly, the database diagram should distinguish canonical service tables from legacy tables and should not describe the schemas as “many logical databases.”

## 4.1.3 Security and Privacy Architecture

Echo processes information that may include personal reflections, assessment responses, identity documents, and support conversations. Its security architecture therefore places authentication, authorization, and data ownership checks at more than one layer. Supabase Authentication issues the user session, the Express API validates the access token and applies feature rules, and PostgreSQL row-level security and database privileges restrict access to user-owned or service-only records. The application also uses input validation, request limits, and separate internal credentials for analysis workers. These controls are present in the repository, although their complete behavior in a deployed environment still requires verification.

Sensitive journal content, Buddy messages, assessment payloads, and selected verification fields are protected by application-managed encryption before storage. The backend retains responsibility for decrypting data when an authorized operation requires it, so this mechanism should be described as encryption at rest in the application data path rather than end-to-end encryption. AI analysis is conditioned on account eligibility, current consent, and the user's decision to request analysis for a particular journal entry. Optional facial capture has an additional privacy preference and must not be described as equivalent to validated facial emotion inference. Crisis information remains reachable without relying on AI availability. The study should present these controls as implemented design measures while reserving claims of complete security compliance for independent and deployed testing.

## 4.2 Application Introduction

Echo is a web-based mental wellness application for the young-adult users described in the study. It brings private journaling, mood review, a supportive Buddy conversation interface, grounding activities, periodic PHQ-8 self-assessment, account settings, and crisis-support information into one user experience. A user signs in, completes the required account and consent steps, and then reaches the dashboard and feature pages. Journal entries and Buddy messages are associated with the authenticated account; the dashboard presents a view of the user's own activity. The application is intended for reflection and access to support information. Its outputs are not a diagnosis or a replacement for a qualified mental-health professional.

The application is under active development. Its interface and database include places for analysis results and progress, but the repository does not yet contain a validated production model that generates journal-based depression severity estimates, text emotion labels, mental-distress classifications, therapeutic recommendations, or facial emotion predictions. The present chapter therefore documents the functions that are implemented and specifies how the proposed intelligent functions will be integrated and evaluated. Results from development fixtures must be identified as simulated and excluded from the study's model-performance claims.

## 4.3 Project Development

Project development followed the functional boundaries established in the system design. The Next.js frontend provides feature-specific views and interaction state; the Express backend accepts authenticated requests and coordinates business rules; and Supabase PostgreSQL stores the resulting account, journal, conversation, activity, and analysis records. A separate FastAPI application defines an internal inference boundary. Versioned database migrations and shared request and response contracts help the components evolve together. The sections below describe the current application path before presenting the proposed integration of trained models.

### 4.3.1 Frontend Development

The frontend is implemented with Next.js, React, TypeScript, and Tailwind CSS. Feature folders contain views, view-model hooks, models, and service adapters so that user-interface behavior can be developed independently from API calls. The journal interface supports entry composition, drafts, submission, and an analysis status experience. The Buddy interface presents messages and browser-based voice controls, while the dashboard displays journal-derived activity and the periodic PHQ-8 check-in. Forms and pages account for loading, errors, and user choices, including the choice to leave a journal entry private without requesting analysis.

The frontend treats analysis as an asynchronous activity rather than assuming that a model returns immediately. After a permitted request, it can display a status projection and retrieve the eventual result through authenticated endpoints. The interface must label development fixtures as simulations and show an unavailable state when the provider is disabled. Before the final evaluation, the researchers should test the complete save-to-result path, keyboard and mobile use, consent changes, and recovery from network or worker failures using the configured deployment, since source code and component tests alone do not demonstrate those outcomes.

### 4.3.2 Backend Development

The main backend uses Node.js, Express, and TypeScript as one modular application. Its versioned routes group functions for registration, access, journals, settings, Buddy and wellness experiences, verification, onboarding, notifications, and internal analysis-worker operations. Controllers validate requests and delegate to services, while services apply ownership, consent, and workflow rules before accessing PostgreSQL. A protected request obtains its identity from the verified session rather than from a user identifier supplied by the browser.

Journal submission is linked to an analysis-request workflow. When analysis is requested and permitted, the backend can create a job and report its status; when the provider is unavailable, the job remains in a waiting state rather than inventing an inference result. An authenticated worker protocol defines claiming, progress, safety, final-result, and failure callbacks with lease and idempotency controls. In the current repository, the in-process provider is disabled by default or uses deterministic development fixtures, and Buddy uses a small rule-based reply function. These paths demonstrate application flow but cannot be reported as trained-model inference.

### 4.3.3 Database Development

Database development uses chronological SQL migrations to define tables, constraints, relationships, indexes, privileges, and row-level security policies. User-owned records carry an account identifier, while service-managed AI records connect analysis requests to journals and results. The canonical database is organized by the eight domain schemas and the `ai_analysis` schema, with a separate `auth_provisioning` schema for registration. An owner-readable `public.analysis_status_projection` supports the progress interface without exposing the private analysis tables directly to the browser. Some older `public` tables remain for compatibility and should be shown separately in a schema diagram.

The design distinguishes original content from derived information. Journal text and selected result payloads use encrypted storage envelopes; analysis requests, progress, model metadata, and audit records use separate tables. The `insights_service.phq8_assessments` table records answers to an actual eight-item questionnaire, with the score computed from those responses inside the trusted backend before the assessment is encrypted. A proposed estimate derived from journal text is a different output and must not be presented as a completed PHQ-8 questionnaire score. A separate schema reference accompanies this draft so each service's tables and relationships can be labeled without placing an unreadable database catalog in the main narrative.

### 4.3.4 AI Model Integration

The proposed integration will build on two request paths that already exist in Echo. Journal analysis will be an asynchronous job because an entry may need several processing stages and should remain saved when an inference component is slow or unavailable. Buddy will use a bounded request and response path because a conversation needs a timely reply. Both paths will call an internal, provider-independent AI layer rather than exposing a model or provider credential to the browser. The first implementation target will be a reliable text-only flow; optional facial processing and generated language will be added only after the underlying consent, output validation, and failure handling have been demonstrated.

The sequence for a journal entry will be: authenticated submission, consent and eligibility check, encrypted save, analysis-job creation, protected worker claim, safety review, validated text analysis, reviewed recommendation selection, encrypted result storage, and owner-only display. The sequence for Buddy will be: authenticated message, safety check, bounded conversation context, internal generation, response validation, encrypted exchange, and display. These sequences are proposed application flows, not a claim that the current repository already performs model inference. The current journal provider is disabled by default or returns explicitly simulated development fixtures; the current Buddy response is rule based; and the FastAPI runtime reports that a validated model is not ready.

#### 4.3.4.1 Internal AI Boundary and Result Contract

Echo will keep Express as the authority for user identity, consent, data access, and persistence. A dedicated Python worker will use the existing authenticated `/api/v1/internal/ai` protocol to report readiness, claim a journal job, maintain its lease, and submit progress, safety, result, or failure callbacks. Express will supply only the journal text needed for that authorized job after decrypting it. The worker will call a model adapter in the internal Python inference application; the browser will have no direct route to that application and the worker will not need direct access to the user's database. This arrangement uses the job tables, worker-health record, and status projection already defined in the codebase while allowing the underlying model or hosting location to change later.

Before real inference is connected, the team will reconcile the two existing response shapes. The FastAPI scaffold currently describes a narrow score-and-severity response, whereas the journal worker callback expects a versioned result containing emotion distribution, distress band, symptom range, recommendation features, provenance, and optional facial data. A single versioned contract will define the request identifier, permitted outputs, model and threshold versions, simulation flag, and validation rules across the Python worker and TypeScript backend. Fields for models that are not yet validated will be nullable or explicitly unavailable in a new contract version; the corresponding progress checks and result views will also show those fields as skipped or unavailable. The system will not fill required fields with guessed values. An invalid response, missing version, timeout, or revoked job will fail safely and remain visible as a status rather than becoming a stored insight.

#### 4.3.4.2 Journal Analysis Workflow

When a user saves a journal, Echo will first preserve the private entry even if analysis cannot run. The existing journal submission and `/journals/:journalId/analyze` routes will check the authenticated owner, current policy acceptance, account eligibility, and the user's entry-specific analysis request. The backend will create one job associated with that journal and expose its limited state through `public.analysis_status_projection`. The frontend can refresh the authoritative status endpoint after a Realtime notification or by polling. If no healthy worker is available, the interface will say that analysis is waiting or unavailable and will not show a fabricated result. Idempotency records will prevent a repeated submission from creating another journal or job.

After claiming a job, the worker will perform a conservative safety pass before ordinary interpretation. A possible immediate-risk signal will pause the analysis in its existing `safety_action_required` state and direct the user to support resources that remain available independently of the model. For an eligible job that can continue, the worker will produce a controlled set of text emotion and distress indicators, each with a confidence or uncertainty measure and a model version. A journal-based symptom estimate will be added only if it is separately validated against the study's reference assessment; it will be labeled as an estimate and kept distinct from the score calculated from the user's actual PHQ-8 questionnaire answers. The backend will validate the complete result, encrypt its payload, save it in `ai_analysis.analysis_results`, update the job and public projection, and allow only that user to retrieve the interpretation.

The application will select an initial coping or reflection activity from the reviewed, versioned rules already represented by `ai_analysis.recommendation_rules` and `recommendation_selections`. This deterministic selection provides a safe baseline that can work without a language model. A generative model may later turn the selected activity into a short supportive explanation, but it will not be permitted to invent a diagnosis, treatment plan, or emergency instruction. Only completed, non-simulated, consented results will be eligible for trend calculations in `insights_service`; fixture data will remain labeled and excluded from research findings. Revoking consent or deleting a journal will stop or invalidate related processing according to the existing lifecycle rules.

#### 4.3.4.3 Buddy Conversation Workflow

Buddy requires a separate integration because it currently produces a rule-based response inside the Express `POST /buddy/messages` request. The proposed change is to place reply generation behind a `BuddyReplyProvider` interface in the backend. After authentication and the existing verification gate, the service will read a limited number of the user's recent messages, decrypt only those needed for context, and send them through an authenticated internal call to a validated conversational provider. The provider will return a structured reply and metadata identifying its version; a separately validated text-emotion label may accompany the message for display in Buddy, but will not be treated as a diagnosis. Express will enforce a short timeout, validate length and safety constraints, and save the user message and accepted reply as encrypted conversation records. A provider failure will return a clear unavailable state so the interface can retain the unsent text instead of presenting a rule-based message as though it were generated by a model.

The safety path will remain independent of conversational generation. Possible urgent language will produce an immediate, reviewed support response and access to the public crisis page even when the language model is down. The model will be instructed to use supportive, non-diagnostic language, but an instruction alone will not be treated as a safety guarantee; representative replies will be tested and reviewed before deployment. Journal text will not be added automatically to Buddy's prompt. If a user explicitly chooses to continue from a journal recommendation, the existing `buddy_service.recommendation_handoffs` record can supply only the approved, limited context and its expiration time. Browser speech recognition and synthesis will remain optional input and output controls around the same Buddy text endpoint rather than separate mental-health inference channels.

#### 4.3.4.4 Optional Facial Processing and User-Facing Insights

The first AI release will remain usable without camera access. Echo already extracts FaceMesh landmarks and blendshapes in a browser worker, but its facial provider currently reports only capture status. The proposed privacy-preserving extension will keep optional facial processing on the user's device and, after separate consent and validation, display a tentative expression observation apart from the text result. Raw frames will not be stored. The present capture contract can transmit a mesh to the backend, so reducing data transfer to an approved derived output would require an explicit contract and interface change before use with participants. The user-facing component will show capture and processing status without a live face preview in the intended experience, and stopping or withdrawing consent will discard the pending capture.

The journal page and dashboard will present text analysis, questionnaire results, and optional facial observations as different sources with clear labels. A weak or unavailable component will be shown as uncertain or unavailable instead of being silently replaced by another modality. The application will not infer concealed emotion from a disagreement between facial and written cues and will not combine the modalities into a depression-severity score without a separately evaluated fusion method. The project's “edge-based” description will apply only to computations actually executed on the user's device or a documented local edge host. Server-side language inference will be described according to its real deployment location and measured latency.

#### 4.3.4.5 Integration Stages and Release Evidence

Implementation will proceed through verifiable stages. The first stage will align the shared result contract and connect one validated text-analysis worker to the existing journal job protocol. The second will add a provider-backed Buddy reply while preserving the independent crisis response. The third will evaluate whether generated recommendation wording or local facial classification adds useful information beyond the simpler reviewed baselines. Each stage will require model-version records, reproducible evaluation on held-out data, failure and timeout tests, consent-withdrawal tests, and an authenticated end-to-end browser flow. The researchers will document accuracy and error rates for classification or estimation, human review of generated advice, response time, resource use, and behavior when a provider is unavailable. Until these checks are complete, the corresponding application feature will remain disabled or explicitly marked as a development simulation.

### 4.3.5 Speech-to-Text and Text-to-Speech Integration

Buddy currently includes optional browser speech recognition for voice input and browser speech synthesis for reading replies aloud. These functions are implemented through browser APIs, and text entry remains available when a browser lacks the capability or microphone permission is refused. The recognition language is presently set to `en-US`; the researchers should evaluate whether this is suitable for the intended participants before claiming support for Filipino or mixed-language speech. Browser speech recognition may depend on the user's browser or platform service, so its data path and limitations should be disclosed before microphone use. Voice support is an accessibility and convenience feature, not evidence that a speech-emotion model has been implemented.

### 4.3.6 FaceMesh Integration

The journal interface has an optional camera component that uses MediaPipe Face Landmarker in a browser worker. With user action and camera permission, it extracts facial landmarks and blendshape values from video frames for a local capture representation. The code also contains a disabled facial-analysis provider, which can record that capture was received but does not return a facial emotion. Thus the current implementation supports an experimental capture path, not a validated Positive, Neutral, or Negative classifier. The final study should not report facial sentiment accuracy or multimodal verification until a classifier is trained, connected, and evaluated with consented samples.

Before participant use, the facial flow should make opting in and stopping capture unambiguous, discard capture data when consent is withdrawn, and explain whether derived landmarks leave the device. The current component renders a live video and mesh preview, so the intended status-only capture experience still requires an interface change. Any future facial classifier should be evaluated separately with a participant-level split, class balance analysis, confidence calibration, and tests across lighting and device conditions. The camera must remain optional, and users who decline it must be able to use journaling and crisis resources without penalty.

### 4.3.7 Security and Privacy Implementation

Security implementation includes server-side request validation, authenticated routes, ownership checks, scoped database access, and controls around sensitive operations. Private data is written through the backend rather than relying on a browser-supplied user identifier. The schema migrations provide row-level security for user-owned records and restrict service-only analysis tables. Encryption envelopes protect journal content, Buddy messages, assessment payloads, and selected other sensitive fields in storage. Analysis requests have consent checks, admission limits, idempotency handling, and audit records to make repeated submission and background processing more predictable.

Several controls still require deployed verification. The study should test account separation, revoked consent, disabled accounts, retention and erasure, document handling, worker-token rotation, database privileges, and recovery from partial failures in the target environment. Security claims should be limited to controls demonstrated by source review, local tests, or deployed tests as appropriate. Formal compliance with a security standard or privacy law should not be claimed solely from the existence of middleware, migrations, or policy documents.

### 4.3.8 Crisis-Support Implementation

Echo provides a public crisis-support route and a directory of reviewed support resources that can be reached independently of Buddy or model inference. The backend has conservative checks for urgent language in the present rule-based Buddy path, and the analysis workflow reserves a safety state for cases requiring review. These mechanisms support prompt access to help, but they do not establish clinical risk prediction. The user should be offered clear emergency and professional support options, with an explanation that Echo does not contact responders or trusted contacts automatically.

The proposed AI safety layer should be tested with direct statements of danger, indirect expressions, mixed languages, negation, quoted text, and ordinary distress. Safety events should contain only the minimum information needed for review, and any escalation involving a trusted contact should require an explicit user action and the applicable permission and review checks. Crisis resources must remain usable when the model is disabled, the network is slow, or the user has not signed in. Clinical reviewers should assess the wording and escalation thresholds before the final system is evaluated with participants.

## 4.4 Development Planning

The remaining development work should proceed in stages that preserve an evaluable application at each step. The first stage will reconcile the FastAPI response and journal callback contracts, connect one text-only worker, and verify consent and failure handling. The second will validate the journal indicators and add a bounded Buddy provider behind the existing message route. The third will assess generated recommendation wording and optional local facial classification against simpler reviewed baselines. Any multimodal fusion should follow only after the separate components and their consent flows are evaluated. Every stage should produce a versioned model artifact or provider record, test results, safety review, and an end-to-end application demonstration before its findings are described as implemented.

### 4.4.1 Software Specifications

The current software stack consists of Next.js and React for the web interface, TypeScript and Express for the main API, Supabase Authentication and PostgreSQL for identity and persistence, and Python with FastAPI and Pydantic for the internal inference boundary. Shared contracts and SQL migrations define the communication and data structures between components. MediaPipe Tasks Vision supports browser-side FaceMesh capture; browser speech recognition and synthesis support the optional voice controls. Training, fine-tuning, and evaluation tools for the proposed language and classification models should be specified only after the researchers pin the actual libraries, artifact versions, licenses, and reproducible environment used in experiments.

### 4.4.2 Hardware Specifications

For ordinary application use, a device with a supported modern browser and network access is needed; a camera and microphone are required only for the optional facial and voice features. The API and database require protected server resources with adequate storage, backup, and network capacity. The proposed language models may require a separate inference host and, depending on precision and throughput, accelerator memory that has not yet been measured in this repository. The study should therefore report actual device models, CPU and GPU specifications, memory, storage, model precision, average and tail latency, and power or cost observations from the final experiments instead of naming an untested minimum hardware configuration. If the project describes itself as edge-based, these measurements should identify which inference components truly execute at the edge.

### 4.4.3 Programming Languages Used

TypeScript is used across the React frontend and Express backend, allowing shared request and response types and strongly typed application modules. Python is used for the FastAPI inference service and is the planned language for model-loading and evaluation work. SQL and PL/pgSQL define the PostgreSQL schemas, constraints, policies, and transactional procedures. CSS and Tailwind utility classes provide the visual presentation of the interface. The choice of languages follows the different responsibilities of user interaction, application coordination, model computation, and persistent data management.

## 4.5 Evaluation of the Project — suggested opening correction

The evaluation of Echo will be conducted after the relevant application paths and proposed intelligent features have been integrated and made available to participants. End-user questionnaires will measure qualities that participants can observe during assigned tasks, while technical tests will evaluate reliability, security, privacy, and performance. Separate model experiments and expert review will assess the validity and safety of the intelligent functions. Features unavailable during a participant's session will be marked not applicable and will not contribute to claims about completed AI functionality. The resulting findings should be presented in Chapter V.

### 4.5.5 Internet and Online Resources

Internet resources used during development include official software documentation, published model and dataset documentation, privacy and security references, and the published contact information of Philippine support organizations. These materials serve different purposes: implementation references inform API behavior, dataset documentation defines provenance and permitted use, and support-resource sources establish the accuracy of public help information. The researchers should record the source, version or retrieval date, applicable license, and any changes made before incorporating a resource into Echo. Public support contacts require periodic rechecking because phone numbers, hours, and service availability can change. Online material will not substitute for the study's own model evaluation, expert validation, or deployed security testing.

## Editorial consistency checks before pasting into the paper

Chapter III currently states in several places that the models were trained, saved, and integrated and that the application produces clinical-style outputs. Those statements should be changed to future tense until the corresponding artifacts, evaluation results, and application integration are documented. The operational framework's `journals`, `mood_checkins`, `conversations`, and `messages` names also need alignment with the canonical service schemas, and a questionnaire PHQ-8 score should remain distinct from a journal-derived estimate. The Chapter III facial “emotion masking” claim requires removal or a carefully defined, independently validated research construct. Chapter IV's database wording should use *logical schemas*, and Section 4.5.4's “questionnaire was used” should remain future tense until responses have actually been collected.
